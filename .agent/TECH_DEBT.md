# Verified Technical Debt

Only evidence-backed debt belongs here. Do not treat an entry as permission to change code outside an approved implementation scope.

This is stable documentation. Every debt entry must be self-contained and durable: do not link to or depend on transient execution reports, temporary prompts, disposable diagnostics, or any other non-stable work product. Stable debt must describe its own scope, evidence requirement, and closure condition directly; transient work products may reference the stable debt owner, never the reverse.

1. **Unknown part dispatch omission** - `prepare(_:)` currently falls through to empty-string rendering for an unknown or unhandled `SwifQLPart`. A new part can therefore be silently omitted if dispatch support is forgotten. This remains verified debt and is not fixed by governance or render scopes.

2. **External `SQLDialect` subclass construction gap** - CLOSED for the audited extension path. An external consumer fixture proved that a downstream module can construct a custom `SQLDialect` subclass and use the additive context-aware rendering hook; `SQLDialect.init()` is public and the established hook remains the default forwarding boundary. Future extension surfaces still require focused external compile coverage.

3. **Generic SQL `name := expression` API is intentionally deferred** - Duck STRUCT/UNION construction/update and macro default/named-call grammar can require `:=`, while table-function options use the distinct `name = value` grammar. The maintainer explicitly deferred a generic public named-argument abstraction from the current Duck closure. Do not improvise a raw-string, product-prefixed, or cross-grammar placeholder. Revisit as a dedicated future API research task with SQL-first call-site examples, Swift naming/operator constraints, and downstream compatibility analysis.

4. **Pre-DESIGN-019 Duck implementation requires retrospective cross-dialect audit before dialect closure** - DESIGN-019 and DIALECT-014 were introduced only after a substantial portion of the Duck SQL-surface implementation had already been independently accepted. Those earlier PASS verdicts therefore do not prove that every shared under-the-hood primitive was shaped against the current cross-dialect semantic-class gate. Before `.duck` may enter `SQLDialect.all` or the Duck closure may be declared complete, independently re-audit the already-accepted pre-star/COLUMNS Duck foundation against current live source. The mandatory scope includes structural SQL-region/root-frame continuation, owner-sensitive clause rendering, builder/subquery/set-result composition, Duck renderer/hybrid behavior, exact base64/Data compatibility, catalog paths, JSON/key-path precedence, scalar/nested types, LIST/ARRAY/MAP values, exact reusable/new functions, SELECT-friendly structural additions, generic SQL lambdas/LIST operations, and joins/set operations. Classify each audited capability as `NO DESIGN-019 IMPACT`, `PASS`, or `CORRECTION REQUIRED`; verify PostgreSQL/MySQL/downstream-extension compatibility and use bounded primary-source evidence from representative external SQL dialect families only where it can reveal a too-narrow shared abstraction. This is an audit obligation, not permission to rewrite accepted behavior speculatively. Every required correction must be separately scoped and independently accepted before this debt is CLOSED.
