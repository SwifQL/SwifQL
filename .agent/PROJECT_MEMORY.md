# Project Memory

This file keeps durable, non-obvious current facts that are useful beyond immediate source inspection. Architecture rules remain in their owners.

- `Package.swift` defines a dependency-free Swift package with one `SwifQL` library target and one `SwifQLTests` test target.
- Production source is under `Sources/SwifQL`; tests are under `Tests/SwifQLTests`.
- PostgreSQL and MySQL are established dialects. Duck is unreleased; current source provides only the minimal `.duck` rendering/context foundation while the broader Duck SQL surface is being designed from current live source and current DuckDB semantics. SwifQL builds SQL only and does not execute DuckDB.
- The compact current pipeline is composable parts -> `prepare(_:)` -> `SwifQLPrepared` and formatter output. See [`DSL_COMPOSITION.md`](architecture/DSL_COMPOSITION.md) and [`QUERY_PREPARATION.md`](architecture/QUERY_PREPARATION.md) for the owning contracts.
- [`DSL_DESIGN_AND_UX.md`](architecture/DSL_DESIGN_AND_UX.md) is the stable owner of the SQL-first public API mental model, API taxonomy, SQL transparency, convenience boundaries, reuse-before-abstraction rule, dialect-transparent user-facing DSL requirement, and new-API checklist. Agents should load it instead of rediscovering these principles from source.
- Dialect documentation is split for context budget: [`DIALECT_RENDERING.md`](architecture/DIALECT_RENDERING.md) owns only cross-dialect rules, while [`dialects/DUCK.md`](architecture/dialects/DUCK.md), [`dialects/POSTGRES.md`](architecture/dialects/POSTGRES.md), and [`dialects/MYSQL.md`](architecture/dialects/MYSQL.md) own per-dialect facts. Load only the relevant dialect owner by default.
- Dialect-specific support does not automatically justify database-prefixed query APIs. Ordinary user source should name clean SQL concepts and let dialect-aware preparation own syntax differences whenever truthful. If a DuckDB-specific Swift implementation symbol genuinely needs a prefix, use `Duck...` / `duck...`, not new `DuckDB...` / `duckDB...` prefixes. The canonical public dialect API is `.duck`, so focused Duck work prepares with `prepare(.duck)`; reserve `"duckdb"` for internal database identity/prose. `SQLDialect.all` remains PostgreSQL + MySQL until Duck passes the explicit final support/compatibility/native-validation closure gate.
- The public library has a substantial historical PostgreSQL-specific surface; another dialect does not automatically make those helpers portable.
- The existing PostgreSQL implementation is the primary local style/organization reference for new dialect code, but target-dialect official documentation owns target SQL semantics.
- Canonical new Swift API uses idiomatic camelCase even when SQL uses snake_case/uppercase. The existing supported surface has completed its additive `Fn` migration: camelCase is the stable implementation/API, while snake_case remains source-compatible as deprecated `renamed:` aliases with identical SQL output.
- Existing PostgreSQL/MySQL query source, generated SQL, bind order, composition behavior, and downstream Swift extensions are compatibility contracts by default.
- The current Duck redesign has explicitly rejected cross-dialect semantic portability facades such as `binary(...)`: exact SQL functions remain exact APIs (`decode` stays `decode`; `from_base64` uses canonical Swift `Fn.fromBase64`, with only a deprecated snake_case bridge if the approved plan includes one). Dialect preparation may adapt the same construct's syntax/casing, not substitute a differently named construct.
- Gate A bounded semantic render scopes and Gate B structural clause ownership are evidence-proven. The accepted major-version Gate B architecture uses generic value-semantic SQL-region/set-result root frames to select open clause ownership through one generic root-frame-aware continuation primitive; dedicated owner-sensitive clauses persist that owner inside `parts`; nested frames isolate statement-local scopes while one renderer/binding collector traverses the structural tree.
